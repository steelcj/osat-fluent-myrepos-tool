# Configuring myrepos (`mr`) for a Development Workspace

If you keep many Git repositories under a common parent directory, `myrepos` (`mr`) provides a convenient way to manage them as a single workspace.

Rather than remembering to visit each repository individually, `mr` lets you execute common Git commands across all registered repositories with a single command.

For example, imagine your repositories are organized like this:

```text
/home/initial/2-areas/development
├── ansible/
├── websites/
│   ├── universalcake/
│   └── client-a/
├── utilities/
│   ├── sat/
│   └── scripts/
└── experiments/
```

The recommended approach is to place a single `.mrconfig` file in the root of the workspace.

```text
/home/initial/2-areas/development/.mrconfig
```

This file serves as the authoritative description of your development workspace. It defines:

- common commands shared by every repository
- the repositories that belong to the workspace
- how missing repositories should be cloned on a new workstation

---

## Creating the workspace configuration

From the root of your development directory:

```bash
cd /home/initial/2-areas/development
nano .mrconfig
```

A good starting point is to define only the common commands in the `[DEFAULT]` section.

```ini
[DEFAULT]

update = git pull --ff-only

status = git status --short --branch

fetch = git fetch --all --prune

push = git push

diff = git diff

branches = git branch -vv

remote = git remote -v

log = git log --oneline --decorate --graph -10

clean = git clean -fd

gc = git gc
```

At this stage, the configuration contains command definitions only. Repository definitions will be added later.

---

## Trusting the configuration

The first time you run `mr`, it will refuse to execute commands from an untrusted configuration file.

For example:

```bash
mr status
```

will produce something similar to:

```text
mr: illegal section "[DEFAULT]" in untrusted /home/initial/2-areas/development/.mrconfig line 1
(To trust this file, list it in ~/.mrtrust.)
```

#### Creating a trust file

Create the trust file in the root of your home directory:

```bash
nano ~/.mrtrust
```

Add the path to your workspace configuration:

```text
/home/initial/2-areas/development/.mrconfig
```

Save the file and rerun the command.

```bash
mr status
```

## Registering existing repositories

`mr` does **not** automatically search your filesystem for Git repositories. Instead, each repository must be registered once. You can do this quickly by creating a loop to register existing (git in this case) repositories for you

### Registering all git repositories in a parent directory

Move into your project directory

```bash
cd /home/initial/2-areas/development
```

Then from the root of the workspace run:

```bash
find . -name .git -type d -prune |
while read -r gitdir; do
    mr register "${gitdir%/.git}"
done
```

Example output:

```text
Registering git url: git@github.com:steelcj/sat.git
Registering git url: git@github.com:steelcj/osat-fluent.git
Registering git url: git@github.com:steelcj/osat-fluent-myrepos-tool.git
Registering git url: git@github.com:steelcj/osat-fluent-rclone-tool.git
```

Each repository should now be add to your project directory  `.mrconfig` file. 

## What `.mrconfig` looks like after registration

After registering repositories, your configuration will contain both the shared commands and repository definitions.

For example:

```ini
[DEFAULT]

checkout = git clone "$MR_REPO" "$MR_REPO_BASENAME"

update = git pull --ff-only

status = git status --short --branch

diff = git diff

push = git push

clean = git clean -fd

branches = git branch -vv

fetch = git fetch --all --prune

log = git log --oneline --decorate --graph -10

remote = git remote -v

gc = git gc

[osat-fluent-rclone-tool]
checkout = git clone 'git@github.com:steelcj/osat-fluent-rclone-tool.git' 'osat-fluent-rclone-tool'

[osat-fluent-sat-tool]
checkout = git clone 'git@github.com:steelcj/osat-fluent-sat-tool.git' 'osat-fluent-sat-tool'

[sat]
checkout = git clone 'git@github.com:steelcj/sat.git' 'sat'

[osat-fluent]
checkout = git clone 'git@github.com:steelcj/osat-fluent.git' 'osat-fluent'

[osat-fluent-myrepos-tool]
checkout = git clone 'git@github.com:steelcj/osat-fluent-myrepos-tool.git' 'osat-fluent-myrepos-tool'
```

The repository sections are normally generated by `mr register` and rarely need to be edited manually.

### Reorganizing

If you reorganize your development project directory structure, rather than manually editing your `.mrconfig` you can just delete all of the repository entires and re-register them once you have finished reorganizing your directory structure.

## Daily workflow 

Once the repositories have been registered, managing the entire workspace becomes straightforward.

Check repository status:

```bash
mr status
```

Fetch updates:

```bash
mr fetch
```

Update every repository:

```bash
mr update
```

View branches:

```bash
mr branches
```

Push local commits:

```bash
mr push
```

View recent history:

```bash
mr log
```

Every command executes in each registered repository.

# Adding a new repository

Suppose you clone a new repository:

Move into it's subdirectory

```bash
cd websites
```

Create your clone

```bash
git clone git@github.com:steelcj/new-site.git
```

Move into your project directory

```bash
cd /home/initial/2-areas/development
```

Register it with the workspace:

```bash
mr register websites/new-site
```



The new repository is appended to `.mrconfig` and automatically participates in future `mr` commands.

# Understanding the `-m` option

Many Git users assume that `mr -m` behaves like `git commit -m`.

It does not.

In `mr`, the `-m` option means **missing is okay**.

It tells `mr` to ignore repositories listed in `.mrconfig` that are not present on the current machine.

This is useful when sharing the same `.mrconfig` across multiple computers where not every repository has been cloned.

For example:

```bash
mr -m update
```

updates every repository that exists locally while silently skipping those that are missing.

It does **not** search the filesystem for Git repositories.

# Improving the update command

To ensure that updates never create merge commits, many developers prefer:

```ini
update = \
    git fetch --all --prune && \
    git merge --ff-only @{u}
```

If your preferred workflow is rebasing, use:

```ini
update = git pull --rebase --autostash
```

# Useful custom commands

Additional commands can easily be added to the `[DEFAULT]` section.

```ini
ahead = git status -sb

incoming = git fetch && git log HEAD..@{u}

outgoing = git log @{u}..HEAD

root = git rev-parse --show-toplevel

origin = git config --get remote.origin.url

last = git log -1 --stat

stash = git stash

unstash = git stash pop
```

These become available exactly like the built-in commands.

For example:

```bash
mr ahead
```

or

```bash
mr outgoing
```

---

# Recommended workflow

For an individual developer maintaining many repositories, a simple workflow works well:

1. Keep a single `.mrconfig` at the root of the development workspace.
2. Define common commands in the `[DEFAULT]` section.
3. Register each repository once using `mr register`.
4. Use `mr` for day-to-day management of the entire workspace.
5. Register newly cloned repositories as they are added.

This approach keeps the workspace reproducible, minimizes maintenance, and makes it easy to manage dozens or even hundreds of repositories from a single location.
